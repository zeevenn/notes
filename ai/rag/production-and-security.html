                                RAG 生产化与安全

                                生产 RAG 同时运行数据流水线和在线查询链路。除了回答质量，还需要保证知识按时更新、用户只能检索授权内容、故障可以定位，并且延迟和成本在负载增长后仍然可控。

                                数据新鲜度

                                索引中的内容是源系统的副本。需要为每种知识源定义：

                                • 更新频率和允许的最大延迟。
                                • 新增、修改、删除和权限变化的同步方式。
                                • 解析失败、Embedding 失败和部分批次失败的重试策略。
                                • 当前索引使用的数据快照、分块算法和模型版本。
                                • 源系统不可用时，旧索引可以继续服务多久。

                                查询结果最好携带 effective_at、updated_at 和索引版本，使过期回答可以追溯。制度类数据还需区分“文件更新时间”和“规则生效时间”。

                                权限必须进入检索链路

                                多租户或内部知识库不能先检索全部内容，再让模型决定哪些可以展示。安全过滤应在候选内容离开检索层之前执行：

                                可信用户身份
    ↓
租户、角色和文档 ACL 过滤
    ↓
只在授权候选中排序和返回

                                ACL（Access Control List，访问控制列表）记录哪些主体可以访问对象。实现时需要注意：

                                • 用户身份和权限条件由服务端生成，而不是从自然语言问题中推断。
                                • 缓存键包含租户、权限范围和索引版本，避免跨用户复用敏感结果。
                                • 引用链接与正文使用相同权限检查，不能只保护原文页面。
                                • 权限撤销要同步到全文索引、向量索引和缓存。
                                • 日志和评估数据也可能包含检索片段，需要单独控制访问和保留期限。

                                Embedding 不是加密后的文本。即使只存向量，也不能把向量库视为公开或低敏感度系统。

                                知识库内容是不可信输入

                                攻击者可能在网页、邮件、简历或共享文档中植入指令。当这些内容被检索进上下文时，会形成间接 Prompt Injection。常见风险包括：

                                • 诱导模型忽略系统指令或泄露提示词。
                                • 诱导 Agent 调用工具、访问链接或发送数据。
                                • 用大量特制文档操纵检索排名，即知识库投毒。
                                • 在图片、隐藏文字或文档元数据中藏入指令。

                                防护需要多层组合：

                                1. 只摄取经过授权和可追踪的知识源。
                                2. 对上传文件执行格式校验、恶意内容扫描和异常检测。
                                3. 在提示词中把检索内容标记为数据，不赋予指令权限。
                                4. 工具调用采用最小权限，并对高风险动作要求确定性校验或人工批准。
                                5. 监控异常查询、异常高频命中和来源集中度。
                                6. 定期以投毒文档、隐藏指令和跨租户问题做回归测试。

                                提示词过滤不能识别所有改写、编码和多模态注入，因此不能作为唯一防线。

                                隐私与数据治理

                                在数据进入外部 Embedding、重排或生成服务前，需要确认：

                                • 数据分类是否允许发送到该服务和区域。
                                • 服务端是否保存输入，保存多久，是否用于训练。
                                • 是否需要删除个人身份信息或业务敏感字段。
                                • 原始文档、向量、缓存、日志和备份如何完成删除请求。
                                • 引用是否会暴露用户本来不知道的文档名称或元数据。

                                不同阶段可能使用不同供应商。数据边界评审要覆盖整个链路，而不是只检查最终使用的生成模型。

                                可观测性

                                一次查询需要生成统一 trace ID，并记录足以复现问题的阶段信息：

                                trace_id
├── 原始查询和规范化查询
├── 用户权限范围与过滤条件
├── 各路召回的文档 ID、排名和分数
├── 融合、去重和重排结果
├── 最终证据 ID 与 token 数
├── 模型、提示词和索引版本
└── 输出引用、延迟、成本与错误

                                Trace（调用轨迹）用于连接一次请求经过的各阶段。日志中是否保存正文，应根据隐私和排障需求权衡；很多场景可以只保存稳定 ID、哈希和受控采样内容。

                                生产监控至少区分：

                                • 摄取延迟、失败文档数和索引版本落后程度。
                                • 检索空结果率、候选数和各数据源命中分布。
                                • 各阶段 P50/P95/P99 延迟和超时率。
                                • 每次请求的 token、重排调用和总体成本。
                                • 无依据回答、拒答、用户负反馈和引用点击。

                                延迟和成本预算

                                端到端延迟可能来自查询改写、Embedding、多个检索源、重排和生成。应为每个阶段设置独立预算和超时，而不是只有一个总超时。

                                常见优化包括：

                                • 缓存稳定文档的 Embedding 和解析结果。
                                • 对重复查询缓存候选 ID，但把权限和索引版本放入缓存键。
                                • 并行执行互不依赖的关键词与向量召回。
                                • 只把必要字段发送给重排器，限制候选数量和长度。
                                • 在质量允许时减少最终证据和生成 token。
                                • 对低风险简单问题跳过查询改写或重排。

                                每项优化都可能影响质量或数据新鲜度，需要在固定评估集上验证。

                                故障与降级

                                组件失败时需要定义明确行为：

                                故障可选降级注意事项
                                向量服务超时只使用关键词检索标记降级并观察召回变化
                                重排器不可用使用融合排名的前 K 条减少 K，避免大量噪声进入上下文
                                某个数据源不可用使用其余来源或停止回答不能暗示结果覆盖了全部来源
                                生成模型超时重试、切换模型或返回检索结果重试要有次数和总体时间上限
                                权限服务不可用拒绝返回受保护内容不能降级为无权限过滤的检索

                                安全边界不能为了可用性而关闭。权限无法确认时应失败关闭（fail closed），即默认不返回数据。

                                发布和回滚

                                索引、模型、提示词和代码都需要版本化。一次发布应记录完整组合，并先通过离线评估，再逐步放量观察线上指标。旧索引需要保留到新版本完成验证，使数据解析错误或召回回归可以快速回滚。

                                生产检查清单：

                                • 是否可以追踪每条回答使用的数据、模型和索引版本？
                                • 文档删除和权限撤销是否覆盖索引与缓存？
                                • 是否有跨租户、投毒和间接 Prompt Injection 测试？
                                • 是否为各阶段设置超时、重试和降级策略？
                                • 是否监控摄取新鲜度、检索质量、延迟和成本？
                                • 是否能在不扩大数据访问范围的前提下复现失败？
                                • 发布前是否运行固定回归集，并支持快速回滚？
