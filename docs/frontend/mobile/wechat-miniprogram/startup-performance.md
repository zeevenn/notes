# 启动与分包加载

打开小程序时，微信客户端需要准备运行环境、获取所需代码并创建入口页面。分包决定哪些代码需要在这次访问中加载，因此会影响启动和页面跳转的等待时间。

## 冷启动与热启动

小程序首次打开，或被销毁后再次打开，需要重新加载运行，称为**冷启动**。如果小程序仍保留在后台，只是重新进入前台，则称为**热启动**。

退出小程序不一定立即销毁它，但后台小程序可能被系统回收。因此，同样是“再次打开”，实际可能是热启动，也可能是冷启动。

代码包缓存和运行状态是两回事：即使需要冷启动，只要本地代码包仍可使用，也不一定需要重新下载。

## 冷启动需要完成哪些工作

官方启动流程以 Android 和 iOS 为主要说明对象，包含以下环节：

1. **准备资源**：建立运行环境，获取或校验小程序的版本、配置和权限信息，准备入口页面所需的代码包。
2. **注入代码**：在逻辑层加载并执行业务 JavaScript，在视图层加载页面结构和样式对应的编译产物。
3. **渲染入口页面**：框架结合初始数据、页面结构和样式生成首屏，完成后触发首个页面的 `onReady`。

这些工作会尽可能并行，例如逻辑层和视图层的代码注入可并行进行，不能把每个阶段的耗时简单相加作为总耗时。

官方启动性能以首个页面的 `onReady` 作为启动完成标志。如果页面主体依赖网络请求，用户可能还要等待响应和后续 `setData` 才能看到内容。因此，还需单独记录业务内容何时展示。

## 主包与分包的加载关系

**主包**包含 `app.js`、全局配置等内容；**分包**按功能保存一组页面、代码和资源，在访问需要它的页面时加载。

假设列表页放在主包，订单详情放在普通分包：从列表进入小程序时，先准备主包；打开订单详情时，再准备对应分包。如果用户通过分享链接直接进入订单详情，启动时仍需要主包和这个普通分包。

**独立分包**可以不依赖主包启动。例如某个独立活动入口，可以只准备该独立分包；之后进入主包或普通分包页面时，再加载主包。相应地，独立入口不能依赖主包中尚未加载的初始化逻辑、全局状态和样式。

普通分包可以使用主包中的公共代码，但不能直接同步引用其他分包的私有文件。共享代码全部留在主包时，即使拆出了很多页面，主包体积也可能下降不多。具体引用规则见[分包文档](https://developers.weixin.qq.com/miniprogram/dev/framework/subpackages/basic.html)。

## 预下载与按需注入

**分包预下载**是在进入某个页面后，提前下载后续可能访问的分包。例如进入商品列表时预下载详情分包，可以减少打开详情时的等待，但会提前消耗流量。配置入口是 `app.json` 的 `preloadRule`。

**按需注入**控制页面和组件代码何时装载到运行环境中，减少当前页面不需要的代码执行。它优化的是代码注入阶段，与代码包是否已经下载是不同问题。

## 按启动阶段定位耗时

| 主要耗时 | 优先检查 |
| --- | --- |
| 代码包准备 | 实际入口需要哪些包、是否命中本地缓存、包体积与网络情况 |
| 代码注入 | 模块初始化、同步存储读取、大量计算、未使用的组件 |
| 首次渲染 | 入口页面的节点规模、参与渲染的组件和初始数据 |
| 首屏业务内容展示 | 请求依赖、返回数据量和后续界面更新 |

微信客户端还可能提前准备部分运行环境，这由客户端策略和设备资源决定，不完全受业务代码控制。测量时应记录设备、入口、代码包缓存与构建版本，并分别比较冷启动和热启动。
