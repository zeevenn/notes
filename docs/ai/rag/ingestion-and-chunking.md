# 数据摄取与分块

RAG 检索的对象通常不是原始文件，而是从文件中提取出的文本片段及其元数据。数据摄取（ingestion）负责把 PDF、网页、数据库记录等知识源转换为这些可检索对象，并在源数据变化后保持同步。

```text
知识源 → 解析 → 清洗与结构恢复 → 分块 → 补充元数据 → 建立索引
```

这一阶段的输出决定了检索系统“能看到什么”。如果表格解析错位、标题被丢弃或权限信息没有进入索引，后续更换 Embedding 模型通常无法弥补这些缺陷。

## 先保留文档结构

不同知识源需要不同的提取方式：

| 知识源 | 需要保留的结构 | 常见失败 |
| --- | --- | --- |
| HTML、Markdown | 标题层级、列表、代码块、链接 | 导航栏和页脚混入正文 |
| PDF | 页码、标题、段落、表格、脚注 | 多栏顺序错乱、扫描页没有文字层 |
| Office 文档 | 标题、表格、批注、章节关系 | 样式信息丢失后无法识别章节 |
| 数据库 | 主键、字段含义、更新时间、权限 | 把多行结构压成不可过滤的长文本 |
| 图片和扫描件 | OCR 文本、版面位置、图片说明 | OCR 错字破坏编号和专有名词 |

OCR（Optical Character Recognition，光学字符识别）用于从扫描图片中提取文字。对表格、图表和多栏 PDF，仅有纯文本往往不够，还需要保留版面或单元格关系。

清洗应删除确实不承载语义的重复页眉、导航和控制字符，但不能为了“干净”而丢失标题、单位、日期、代码缩进等检索所需信息。清洗前后的内容最好可以追溯到原始文件和位置。

## Chunk 是检索单元

Chunk 是索引和召回使用的文本片段。它需要同时满足两个条件：

- 足够小，使内容围绕一个主题，查询可以准确命中。
- 足够完整，使片段包含回答问题所需的上下文。

不存在适用于所有数据集的固定大小。合理的边界取决于文档结构、问题粒度、Embedding 模型限制和生成阶段的上下文预算，最终需要通过评估确定。

### 固定长度分块

按字符或 token 数切分，实现简单，适合结构很弱的纯文本。通常会设置少量 overlap（重叠），避免一个句子或定义正好跨越边界。

```text
chunk 1: token 0 ───────── 399
chunk 2:             320 ───────── 719
                     ← 80 token overlap →
```

固定长度可能从段落中间截断内容。重叠过小会丢失边界上下文，过大则会增加索引体积，并让查询结果出现多个高度重复的片段。

### 按结构分块

技术文档、制度和代码通常有明确结构，优先按标题、段落、列表、表格或函数边界切分，再对过长区块递归切分：

```text
文档
├── 二级标题 A
│   ├── 段落 1
│   └── 段落 2
└── 二级标题 B
    └── 表格 1
```

每个片段应携带完整标题路径，例如“员工制度 > 休假管理 > 年假”，使脱离原文的片段仍然能被定位和理解。

### 父子分块

检索需要短而聚焦的片段，生成却可能需要更完整的段落。父子分块会索引较小的子块，命中后再返回对应的大段父块：

```text
检索：子块“试用期年假为 3 天”
返回：包含适用范围、例外和审批流程的完整章节
```

这种方式也称为 Small-to-Big Retrieval。它增加了索引关系和上下文选择逻辑，适合短片段经常缺少限定条件的数据集。

## 为片段补充上下文

原文中的代词、简称和局部数字在切分后可能失去指代。例如片段只有“本季度增长 3%”，无法判断主体和时间。常见处理方式包括：

- 在片段前保留文档标题和章节路径。
- 保存前后相邻片段的引用，命中后按需扩展。
- 为片段生成简短的上下文说明，再用于关键词和向量索引。
- 为表格行补充表头、单位和统计周期。

自动生成的说明也可能引入错误，因此原始片段与补充文本应分字段保存，并在评估中分别验证。

## 元数据与来源定位

元数据用于过滤、权限检查、引用和数据维护。一个片段至少应保留稳定标识、来源位置和版本信息：

```json
{
  "chunk_id": "employee-handbook:2026-07:leave:03",
  "document_id": "employee-handbook",
  "title": "员工手册",
  "section_path": ["休假管理", "年假"],
  "source_uri": "/policies/employee-handbook.pdf",
  "page": 18,
  "updated_at": "2026-07-15T09:30:00+08:00",
  "version": "2026-07",
  "language": "zh-CN",
  "access_groups": ["employees"]
}
```

不要把所有元数据拼进一个文本字段。日期、租户、部门和权限组应使用可过滤字段；标题和摘要可以同时进入全文索引和向量表示。

## 更新、删除与重建

知识库不是一次性导入任务。摄取流水线需要处理：

1. 根据源文档 ID 和内容哈希识别新增、修改和未变化的文档。
2. 删除旧版本产生的片段，避免新旧制度同时被召回。
3. 只重新解析和嵌入发生变化的内容。
4. 在 Embedding 模型、分块算法或元数据模式变化时创建新索引版本。
5. 验证新索引后再切换查询流量，并保留可回滚的旧版本。

如果业务要求删除个人数据，仅删除原文件不够；缓存、全文索引、向量索引和评估样本中的副本也需要进入删除流程。

## 摄取质量检查

建立索引前可抽样检查：

- 文档数量、页数和片段数量是否符合预期。
- 标题、表格、代码和列表是否保持正确顺序。
- 每个片段能否定位到原文页面或章节。
- 单个片段是否包含多个互不相关主题。
- 限定条件是否因切分而落在另一个片段中。
- 重复片段和模板文本是否占据大量索引。
- 更新时间、版本和访问权限是否完整。
- 扫描件、空文件和解析失败是否有单独的错误队列。

分块质量必须在真实问题上评估。仅观察平均 chunk 长度，无法判断用户需要的证据是否仍然完整。
