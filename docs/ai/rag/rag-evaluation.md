# RAG 评估

RAG 的最终回答依赖多个阶段。回答错误时，需要先判断正确证据是否进入候选集，再判断重排和生成是否正确使用证据。

```text
数据质量 → 召回 → 重排 → 上下文构造 → 生成 → 引用
```

只评最终回答会掩盖根因。例如模型根据给定证据生成了忠实回答，但检索到的是过期制度；此时生成忠实度很高，端到端答案仍然错误。

## 黄金评估集

黄金评估集是一组经过审核的问题、证据和期望结果。一个样本可以包含：

```json
{
  "query": "试用期员工有几天年假？",
  "query_type": "single-hop",
  "filters": { "effective_at": "2026-08-01" },
  "relevant_chunk_ids": ["employee-handbook:2026-07:leave:03"],
  "reference_answer": "每个自然年 3 天。",
  "required_claims": ["试用期员工每个自然年有 3 天年假"],
  "must_abstain": false
}
```

评估集应覆盖：

- 高频事实问答、定义和操作步骤。
- 使用简称、错别字和同义表达的问题。
- 依赖多个片段或多个来源的问题。
- 多轮对话中的省略和指代。
- 没有答案、证据不足或来源冲突的问题。
- 旧版本、权限隔离和时效过滤场景。
- 历史线上失败和安全对抗样本。

不能只由模型从现有文档自动生成评估问题。自动生成适合扩大覆盖，但容易偏向文档措辞和容易定位的事实；真实用户查询和人工审核仍然必要。

## 检索评估

检索评估不调用生成模型，直接比较返回结果和标注的相关片段。

### Recall@K

Recall@K（前 K 条召回率）表示所有相关片段中，有多少出现在前 K 个结果内：

```text
Recall@K = 前 K 条中的相关片段数 / 全部相关片段数
```

如果问题需要的唯一证据没有出现在 Top-K，生成模型通常无法可靠回答。多证据问题需要明确是“至少找到一个”还是“必须找全所有证据”。

### Precision@K

Precision@K（前 K 条精确率）表示前 K 个结果中有多少真正相关：

```text
Precision@K = 前 K 条中的相关片段数 / K
```

低精确率意味着大量无关内容会进入重排或上下文，增加成本并稀释证据。

### MRR 和 NDCG

MRR（Mean Reciprocal Rank，平均倒数排名）关注第一个相关结果出现得有多靠前，适合每个问题通常只有一个主要答案的场景。

NDCG（Normalized Discounted Cumulative Gain，归一化折损累计增益）允许给结果标注多个相关等级，并对靠前的高相关结果给予更高权重，适合存在“直接证据、辅助证据、主题相关”等等级的场景。

检索指标应按问题类型、语言、数据源和权限组切片。总体均值可能掩盖某一部门或某类文档完全无法召回的问题。

## 重排评估

重排需要同时比较重排前后的结果：

- Recall@N：初始候选集是否包含所需证据。
- Recall@K、MRR 或 NDCG@K：重排后证据是否进入较小的最终集合。
- 重排耗时和成本：质量收益是否值得额外调用。

如果正确证据没有进入初始 Top-N，调整重排器没有作用；需要回到分块、查询处理和召回阶段。

## 生成评估

为了隔离生成能力，可以先给模型提供人工确认的正确证据，再测量：

| 维度 | 要回答的问题 |
| --- | --- |
| 正确性 | 回答是否符合参考答案和业务规则 |
| 忠实度 | 回答中的事实是否都能从给定证据推出 |
| 完整性 | 问题要求的关键结论是否遗漏 |
| 相关性 | 是否直接回答问题而没有引入无关内容 |
| 拒答正确性 | 证据不足时是否停止推测 |
| 指令遵循 | 是否满足语言、格式和安全约束 |

LLM-as-judge 可以按评分标准批量辅助评审，但 Judge 模型也可能偏好特定文风、长度或模型输出。应固定 Judge 提示词和版本，并抽样进行人工复核。

## 引用评估

引用不能只检查“有没有链接”。至少测量：

- **Citation correctness**：引用片段是否支持它旁边的结论。
- **Citation completeness**：需要外部证据的结论是否都有引用。
- **Citation validity**：文档、章节、页码或 URL 是否真实存在且用户有权访问。

可以先把回答拆成独立事实声明，再让评审者逐条判断支持关系。数字、日期、否定和适用条件应单独检查，因为部分支持不等于完整支持。

## 端到端指标

检索和生成分别达到基线后，再测量完整系统：

- 任务成功率和人工可接受率。
- 正确拒答率与错误拒答率。
- P50、P95 和 P99 延迟。
- 每次查询的 Embedding、检索、重排和生成成本。
- 输入与输出 token 数量。
- 错误率、超时率和降级路径触发率。

高平均分不能代替高风险场景的最低要求。涉及财务、医疗、法律或权限数据时，应为关键切片设置单独门槛。

## 受控实验

每次实验只改变一个主要变量：

1. 固定评估集、生成模型和提示词，比较分块策略。
2. 固定索引，比较 BM25、向量和混合召回。
3. 固定候选集，比较重排器和最终 Top-K。
4. 固定证据，比较上下文顺序、压缩和生成提示词。
5. 记录模型、索引、代码、数据快照和参数版本。

同时修改多个阶段，即使最终分数提高，也无法判断哪一项有效，后续回归时也难以定位。

## 从线上失败回到评估集

线上日志应能重放一次查询的关键轨迹，但需要按隐私政策脱敏和限制保留时间。每个失败案例可以归入：

- 知识库中没有对应内容。
- 解析或分块丢失信息。
- 权限或业务过滤错误。
- 召回遗漏或重排降级。
- 上下文截断、冲突或重复。
- 模型误读证据或生成无依据结论。
- 引用映射或界面展示错误。

确认根因后，把案例和正确证据加入回归集。评估集由真实失败持续增长，比一次性追求大量合成样本更有价值。
